# Simulation data for teaching — how a pack is built

Simulation packs give a classroom a few weeks of **fictional** security-operations activity for a teaching case: telemetry sources, detection rules and their tests, alerts, threat indicators, playbooks, cases, approvals and recorded response actions, plus the teaching material around them (learning objectives, a day-by-day storyline and exercises with their expected findings).

A pack is imported into a workspace from **Settings → Simulation data**, through the same importers as any local SIEM or SOAR file (`crg-siem-import/1`, `crg-soar-import/1`, see [SIEM-SOAR-IMPORT-FORMAT.md](SIEM-SOAR-IMPORT-FORMAT.md)). Every imported record is marked `simulation: true` and `simPack: <pack id>` and can be removed from the same screen.

This guide is the knowledge needed to build a new pack — by hand, with a script like `data/simulation/medibec/build-medibec.mjs`, or with the **Generate with AI** function (whose prompt is assembled from these rules by `buildPrompt()` in `js/simgen.js`). `validatePack()` in the same file checks a pack mechanically against the workspace it is meant for.

## 1. What a pack is

```
data/simulation/
  index.json                       {"format":"crg-simulation-index/1","packs":[{id, path, case, title, language, fictional}]}
  <case>/manifest.json             crg-simulation-pack/1 — the teaching manifest
  <case>/siem.json                 crg-siem-import/1  — telemetry, rules, tests, alerts, indicators, gaps, coverage, events
  <case>/soar.json                 crg-soar-import/1  — gates, playbooks, cases, approvals, executions, simulations, lessons, artefacts
  <case>/build-<case>.mjs          optional: the script that writes the three files (edit it, not the JSON)
```

A pack that is downloaded, opened from a file or generated by AI is **one JSON object**: the manifest with the two files inline as `siem` and `soar`.

### Manifest (`crg-simulation-pack/1`)

| Field | Required | Meaning |
|---|---|---|
| `format` | yes | `"crg-simulation-pack/1"` |
| `id` | yes | lower-case, digits and hyphens: `<case>-<focus>-<year>`, e.g. `medibec-ransomware-2026` |
| `version`, `created`, `author`, `license` | no | |
| `title`, `description` | yes | shown to the educator |
| `case` | yes | teaching case id (`medibec`); the workspace must hold the scenario and crown-jewel ids the pack cites |
| `fictional` | yes | always `true` |
| `language` | no | `en` or `fr` — the language of the texts; `i18n.fr` / `i18n.en` may carry a translation of title, description, learningObjectives, storyline (title, text) and exercises (question, screen, expected) |
| `asOfHint`, `timezone` | no | the as-of date from which the teaching points hold; the time zone the times are written in |
| `scenarios`, `crownJewels` | no | ids of the workspace the storyline exercises |
| `people` | no | fictional people, each followed by "(fictional)" |
| `learningObjectives` | yes | 5–9 sentences |
| `storyline` | yes | `[{day, date, title, text, alerts:[ids]}]`, one entry per day |
| `exercises` | yes | `[{id, question, screen, route, expected}]` — `route` is the in-app link (`#/siem/alerts`) |
| `expectedImport` | recommended | counts the import must report (`{siem:{alerts:40,…}, soar:{cases:4,…}, soarSkipped:[{list,id,why}]}`) — the regression test reads it |
| `files` | yes for bundled packs | `[{path, format, module}]` |
| `siem`, `soar` | inline packs | the two documents, each with `"simulation": true` |

The schema as a JavaScript object is `PACK_SCHEMA` in `js/simgen.js`.

## 2. Designing the storyline

1. **Start from the case, not from the attack.** Read the workspace: organization profile, crown jewels (`ws.assessment.CROWN`), risk scenarios and the ATT&CK techniques the analyst linked to them (`SCEN[].attack`), assets. Choose one or two scenarios the intrusion chain will exercise (MediBec: S1 credential compromise and S2 ransomware, with S3 backups, S4 cloud storage, S5 service-account misuse along the way).
2. **One intrusion chain, causal and dated.** Initial access → execution → persistence → credential abuse → lateral movement → collection → exfiltration → impact, each step one or two alerts, each on a plausible host. The chain must reach at least one crown jewel.
3. **Mostly noise.** In real queues most alerts are routine. Aim for roughly 40 % benign or false positive, 40 % intrusion, 20 % other untriaged activity. False positives should come from the *same* rules as true positives (a partner transfer tripping the exfiltration rule, a migration job tripping the encryption rule).
4. **Make mistakes visible.** A true positive closed as benign, a case closed too early, a beacon left untriaged — the students find them.
5. **Length.** 7, 14 or 21 days; 25–40 alerts for three weeks. Test and rule dates fall before the storyline (they are the detection programme's history); the storyline ends a few days before the date the pack is used.
6. **People.** Five to seven fictional roles: two analysts, a SOC lead, a CISO, an IT operations manager, a service-desk technician (no approval authority) — enough to show independence and authority.

## 3. The required mix — every teaching point must appear

| Teaching point | What the data must contain | Where students see it |
|---|---|---|
| Alert ≠ incident | alerts and cases, **no** `confirmations`; no alert `triage: "escalated"` | SOAR → Cases (confirm an incident by name and date) |
| Triage by crown jewel | critical alerts on crown jewels (`asset: "CJ1"`…) mixed with older non-crown alerts | SIEM → Alerts & triage (crown jewels first) |
| Benign / false positive / untriaged | `triage` values `benign`, `false-positive`, `in-triage`, `new` | SIEM → Alerts & triage |
| Coverage validated only by tests | production rules with an **effective** test of the current version; one with an **ineffective** latest test; one production rule **never tested**; one test of an older version only | SIEM → Coverage & gaps |
| Telemetry health | sources **healthy**, **degraded** and **silent** (`healthHistory`), and one **stale** source (`lastSeen` older than 3 × `cadenceHours`) | SIEM → Telemetry sources; rules relying on them become *degraded* |
| Blind spot | an attack step whose detecting rule needs a silent source → **no alert**, told in the storyline, recorded as a gap | SIEM → Coverage & gaps |
| Rule lifecycle | rules in `production`, `testing`, `draft`, `disabled` (with `history`) | SIEM → Detection rules |
| TLP 2.0 | indicators `CLEAR`, `GREEN`, `AMBER`, one **`AMBER+STRICT`**, one **`RED`**; an alert may carry RED | SIEM → Indicators & TLP; exports leave restricted rows out |
| Stale intelligence | one indicator `revoked: true`, one with `validUntil` before the as-of date | SIEM → Indicators & TLP |
| Confidence ≠ probability | `confidence` 0–100 with a `confidenceMethod` saying so; an exercise asking whether it can be a Pb(A) (answer: no) | — |
| Approvals | a valid specific approval; an **expired** pre-authorisation; a **revoked** approval followed by the action; a **self-approval** attempt (the import refuses it: expected skip); an approval by someone outside the gate authorities (**wrong-authority**); a **rejected** approval followed by an attempt (**not-granted**); a gated action with **no** approval (**absent**); a `requested` approval still pending | SOAR → Actions (executions without valid approval) |
| Playbooks | versions `retired`, `published`, `draft`; simulations **passed** and **failed**; one playbook never simulated | SOAR → Playbooks, Simulations |
| Case lifecycle | cases at several statuses (`investigating`, `contained`, `eradicated`, `closed`) with `statusDates` and a timeline | SOAR → Cases |

`validatePack()` reports a missing point as a warning ("Teaching point missing: …").

## 4. Mapping to the case

- Scenario ids (`S1`…) in `rules[].scenarios`, `alerts[].scenarios`, `gaps[].scenario`, `coverage[].scenario`, `playbooks[].scenarios`, `simulations[].scenario`, `lessons[].scenarios` **must exist** in the workspace (error otherwise).
- `alerts[].asset`, `sources[].asset`, `cases[].assets`: a crown-jewel id (`CJ1`) that exists (error otherwise), an asset id or name of the workspace, or empty. Host names (`SRV-EHR-APP02`, `WS-GAT-014`) go into titles, `target` and timelines, not into `asset` (a warning says so).
- Techniques: real ATT&CK Enterprise ids that fit the event — prefer those the analyst already linked to the scenario. Leave empty rather than guess.
- Never touch risk parameters, CVSS vectors, appetite or measures: a pack is operational evidence, not an assessment.

## 5. Realism rules

- Times: one zone for the whole pack, written `YYYY-MM-DDTHH:MM:SS` without a zone; say which in `timezone`. Night-time for the attacker, office hours for the noise.
- Alerts carry `externalId`, `sourceSystem`, `ruleId` (when a rule fired), `detected`, `severity`, `confidence`, `events` as **pointers** (`ref`, `sourceId`, `sourceTime`, `hash`) — never a payload.
- Rules: Sigma-like rules carry `language: "sigma"`, `logsource` and the `detection` block as text; native and correlation rules a one-line query.
- Severity is the SIEM's; the triage queue weighs it with crown-jewel status and asset criticality.
- Indicators come from fictional producers (ISAC, partner CERT, law-enforcement liaison, the SOC itself) whose names say "(fictional)".

## 6. Fictional-data safeguards

| Kind | Allowed | Checked by `validatePack` |
|---|---|---|
| IPv4 | `192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24` (RFC 5737) — anywhere in the pack | error |
| IPv6 | `2001:db8::/32` (RFC 3849) | error (indicators) |
| Domains, URLs, e-mail | `example.com`, `example.net`, `example.org` and subdomains; `*.example`, `*.test`, `*.invalid`, `*.localhost` (RFC 2606, RFC 6761) | error |
| Hashes | made-up hexadecimal (e.g. SHA-256 of a descriptive string) — never a hash of a real file | hexadecimal only |
| Names | fictional people, producers and source systems marked "(fictional)" or "Simulated …"; no real malware family, threat actor or vendor product | warning (source systems, indicator sources) |
| Markings | `fictional: true`; `simulation: true` on both envelopes (error) and on every record (warning) | |
| Internal names | free (`SRV-EHR-APP02`, `adm.jdupuis`) — they exist only in the case | — |

The import marks every record it adds with `simulation: true` and `simPack` even when the file forgot it.

## 7. Validation checklist

1. `validatePack(pack, ws)` returns `ok: true` in a workspace of the case (and errors in a workspace of another case).
2. Warnings read and accepted — the only expected ones are deliberate (e.g. the self-approval attempt).
3. Import in a fresh copy of the case: no SIEM error; SOAR skips only what `expectedImport.soarSkipped` lists; counts equal `expectedImport`.
4. Coverage at the as-of date shows validated, untested, degraded and missing; the telemetry screen shows healthy, degraded and silent sources.
5. The triage queue starts with crown-jewel alerts.
6. SOAR lists executions without valid approval with the reasons the storyline intends (expired, revoked, absent, wrong-authority, not-granted).
7. No incident was created by the import; no alert is escalated.
8. Every exercise can be answered from the screen it names, and its expected finding matches what the screen shows.
9. Re-importing adds nothing on the SIEM side (duplicates); **Remove simulation data** leaves the workspace as before.
10. The regression test (`tests/t19_simulation.mjs` for MediBec) passes.

## 8. Generating a pack with AI

**Settings → Simulation data → Generate with AI** (task `simulation_pack`). The request is assembled by `buildPrompt(ws, options)`:

- from the **current workspace only**: organization profile fields, scenarios (id, name, ATT&CK techniques), crown jewels (id, name, dependencies) and information assets — no documents, notes, risk figures, budget or keys;
- the rules of sections 3–6 (`GUIDE_RULES`) and the format (`FORMAT_SPEC`);
- the options: storyline length, intensity, focus (ransomware, phishing and account takeover, insider, supplier, cloud, mixed), number of alerts, language of the texts.

The educator sees and may edit the exact payload before it is sent (same preview, routing policy, consent and AI log as every AI feature). The answer is parsed, labelled "generated with AI — Analytical estimate — validation required", validated with `validatePack`, and can be downloaded or imported only when it has no error. Review the warnings and the exercises before using a generated pack in class: the model writes plausible data, not verified teaching material.

## 9. Adding a pack to the bundle

1. Write `data/simulation/<case>/build-<case>.mjs` (copy the MediBec one), run it, and add the entry to `data/simulation/index.json`.
2. Run the checklist of section 7; add a regression test modelled on `t19_simulation.mjs`.
3. Add the files to the service-worker precache list if the pack must work offline.
