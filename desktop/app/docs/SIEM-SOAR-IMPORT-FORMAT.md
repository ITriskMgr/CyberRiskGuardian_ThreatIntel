# SIEM and SOAR import formats

Local JSON files read by the SIEM and SOAR modules. Nothing connects to a live product.

## SIEM

Envelope `crg-siem-import/1` — one JSON file that the SIEM screen (**SIEM → Import**, or the import button of **Detection rules** and **Alerts & triage**) reads from this computer. Nothing is fetched from a network: the file is exported from your tools (or generated by the simulation-data builder) and opened locally. The importer is `importText()` in `js/siem.js`.

### General rules

- Encoding UTF-8, one JSON object. Unknown top-level keys and unknown record fields are ignored.
- Every top-level list is optional; when present it must be a JSON array (otherwise the import stops with an error and adds nothing from that list).
- Dates are ISO 8601: `YYYY-MM-DD` for dates, `YYYY-MM-DDThh:mm:ssZ` (or without `Z`) for date-times. Comparisons with the as-of date use the first 10 characters.
- Identifiers (`id`) are the application's local identifiers (strings). Keep them stable across files: they are the deduplication keys. When `id` is missing the application assigns one (`TS-001`, `DR-001`, `DT-001`, `AL-001`, `IND-001`, `GAP-001`, `COV-001`, `DS-001`, `EV-001`).
- Cross-references use those ids: `rules[].requiredSources` → `sources[].id`; `tests[].ruleId` and `alerts[].ruleId` → `rules[].id` (an alert may also give the rule's external `ruleId`); `alerts[].indicators` → `indicators[].id`; `rules[].scenarios`, `gaps[].scenario`, `coverage[].scenario` → risk scenario ids of the workspace (`S1`, `S2`…); `alerts[].asset` and `sources[].asset` → asset id or asset name of the workspace (or a crown-jewel id `CJ1` / name).
- Lists of strings may be given as JSON arrays (preferred) or as one string separated by `;`, `,` or `|`.
- Records are added, never silently overwritten. Re-importing the same file adds nothing (duplicates are counted). See *Deduplication* below.
- Every import is recorded in `ws.siem.imports` (date-time, file name, kind, counts, SHA-256 of the file text, user, messages) and in the data log.
- The processing order is: sources, strategies, rules, tests, indicators, (STIX sightings), alerts, gaps, coverage, events — so a file can reference records it creates itself.

|---|---|---|---|

| `source` | string | no | tool or person that produced the file (informational; `producer` accepted) |

| `sources` | array of *source* | no | telemetry sources and their health |
| `strategies` | array of *strategy* | no | detection strategies adapted from ATT&CK |
| `rules` | array of *rule* | no | detection rules |
| `tests` | array of *test* | no | detection tests |

### `sources[]` — telemetry source (CRGO *telemetry source*, CRGO_0001097)

| Field | Type | Required | Allowed values / meaning |
|---|---|---|---|
| `id` | string | recommended | local id, e.g. `TS-IDP` |
| `name` | string | **yes** | e.g. `Identity provider sign-in logs` |
| `system` | string | no | source system exporting it (CRGO *source system*) |
| `asset` | string | no | asset id or name (CRGO *source asset*) |
| `sourceType` | string | no | free text, e.g. `identity provider sign-in log` |
| `ocsfClass` | integer or string | no | OCSF 1.9.0 event class the source is normalised to: class uid (`3002`), class name (`authentication`) or caption (`Authentication`). Unknown values are dropped. |
| `dataComponents` | array of string | no | ATT&CK data components `DC####` |
| `parser` | string | no | parser name |
| `parserVersion` | string | no | parser version |
| `logsource` | object | no | Sigma-style `{ "product", "service", "category" }` (strings); used to propose the required telemetry of imported Sigma rules |
| `cadenceHours` | number | no | expected hours between events; a source whose `lastSeen` is older than 3 × cadence at the as-of date is shown **silent (stale)** |
| `lastSeen` | date-time | no | time of the last event received |
| `health` | string | no | `healthy`, `degraded`, `silent`, `unknown` (default `unknown`) |
| `healthDate` | date | no | date of that observation (default: import date) |
| `healthHistory` | array | no | dated observations `{ "date": "YYYY-MM-DD", "state": "healthy"\|"degraded"\|"silent"\|"unknown", "note": "…" }` (CRGO *telemetry health observation*). The state at an as-of date is the latest observation on or before it. |
| `notes` | string | no | |

| `level` | string | no | `informational`, `low`, `medium`, `high`, `critical` |
| `description` | string | no | |

### `tests[]` — detection test (CRGO *detection test*, CRGO_0001108)

| Field | Type | Required | Allowed values / meaning |
|---|---|---|---|
| `id` | string | recommended | e.g. `DT-RW-2026-06` |
| `ruleId` | string | **yes** | `rules[].id` |

| `result` | string | **yes** | `effective` or `ineffective` |
| `method` | string | no | `replay`, `emulation`, `purple-team`, `unit`, `other` |

| `evidence` | string | no | id in the shared evidence register |
| `notes` | string | no | |

### `alerts[]` — security alert (CRGO *alert*, CRGO_0000551) — never an incident

| Field | Type | Required | Allowed values / meaning |
|---|---|---|---|
| `id` | string | no | local id (assigned when missing) |
| `externalId` | string | recommended | id in the SIEM; deduplication key with `sourceSystem` and `version` |
| `version` | integer | no | default `1` |
| `sourceSystem` | string | recommended | SIEM that raised it |
| `title` | string | **yes** | |
| `ruleId` | string | no | `rules[].id` or the rule's external `ruleId` (CRGO *generated by rule*) |
| `ruleVersion` | string | no | version of the rule that fired (default: the rule's current version at import) |
| `detected` | date-time | recommended | detection time |
| `firstSeen` | date-time | no | first event time |
| `severity` | string | no | `low`, `medium` (default), `high`, `critical` (`informational` → `low`) |
| `confidence` | number 0–100 | no | confidence stated by the source; **not a probability**, never used in risk parameters |
| `asset` | string | no | asset id or name, or crown-jewel id/name (CRGO *involves asset*); drives triage priority |
| `techniques` | array of string | no | `T####` |
| `scenarios` | array of string | no | scenario ids |
| `indicators` | array of string | no | `indicators[].id` matched (CRGO *matched indicator*; never an attribution) |
| `ocsfClass` | integer or string | no | default `2004` (Detection Finding) |
| `events` | array | no | pointers `{ "ref": "…" (required), "sourceId": "TS-…", "sourceTime": date-time, "hash": "sha256:…", "ocsfClass": 3002 }` — never the payload |
| `rawRef` | string | no | link to the raw event in the SIEM (must not carry credentials) |
| `tlp` | string | no | TLP 2.0 (default: envelope `tlp`, else the import choice) |
| `triage` | string | no | `new` (default), `in-triage`, `benign`, `false-positive`. `escalated` is not accepted from a file: escalation is done in the application and opens a SOAR case. |
| `assignee` | string | no | |

The record as imported is kept verbatim (`original`, up to 4,000 characters) and never modified.

### `indicators[]` — threat indicator (CRGO *threat indicator*, CRGO_0001104)

| Field | Type | Required | Allowed values / meaning |
|---|---|---|---|
| `id` | string | recommended | e.g. `IND-PHISH-DOMAIN` |
| `stixId` | string | no | STIX id `indicator--…`; deduplication key |
| `type` | string | no | `domain-name`, `ipv4-addr`, `ipv6-addr`, `url`, `email-addr`, `file:sha256`, `file:sha1`, `file:md5`, `other` — guessed from `value` when missing |
| `value` | string | **yes, or `pattern`** | the observable |
| `pattern` | string | no | STIX pattern, e.g. `[domain-name:value = 'login-example.test']`; generated from type and value when missing; type and value are read from a simple pattern when `value` is missing |
| `patternType` | string | no | default `stix` |
| `name` | string | no | |
| `validFrom`, `validUntil` | date or date-time | no | after `validUntil` the indicator is **stale** and supports no inference |
| `confidence` | number 0–100 | no | source confidence as stated; **not a probability** |
| `confidenceMethod` | string | no | how the source states it, e.g. `STIX 2.1 confidence, 0-100, as given by the feed` |
| `source` | string | no | intelligence source (CRGO *indicator from source*) |
| `tlp` | string | no | TLP 2.0 marking (CRGO *has information marking*) |
| `labels` | array of string | no | |
| `techniques` | array of string | no | `T####` |
| `revoked` | boolean | no | revoked by the producer (stale) |

### `gaps[]` — detection gap (CRGO *detection gap*, CRGO_0001107)

| Field | Type | Required | Meaning |
|---|---|---|---|
| `id` | string | recommended | |
| `title` | string | **yes** (shown) | |
| `scenario` | string | no | scenario id |
| `technique` | string | no | `T####` (CRGO *gap for technique*) |
| `source` | string | no | `sources[].id` missing or silent (CRGO *gap in telemetry*) |
| `description`, `owner` | string | no | |
| `status` | string | no | `open` (default), `accepted`, `closed` |
| `raised` | date | no | |
| `actions` | array of string | no | ids of corrective actions in the shared register (`ACT-…`) |

### `coverage[]` — coverage assertion (CRGO *detection coverage*, CRGO_0001106)

| Field | Type | Required | Meaning |
|---|---|---|---|
| `id` | string | recommended | |
| `scenario` | string | no | scenario id |
| `technique` | string | no | `T####` |
| `rules` | array of string | no | `rules[].id` claimed to provide the coverage |
| `note` | string | no | |

An assertion never states a status: the application computes it at the as-of date — **validated** (rule in production, latest test on or before the date effective, required telemetry neither silent nor degraded), **untested**, **degraded** (rule in testing, required telemetry silent/degraded/unregistered, or latest test ineffective) or **missing** (no rule, or rules draft/disabled/retired or created later). A required source that is not in `sources` counts as silent.

### `events[]` — security event record (CRGO *security event record*, CRGO_0001098) — a pointer

| Field | Type | Required | Meaning |
|---|---|---|---|
| `id` | string | recommended | |
| `externalRef` | string | **yes** | reference of the event in the SIEM |
| `sourceId` | string | no | `sources[].id` (CRGO *emitted by*) |
| `observed` | date-time | no | event time |
| `recorded` | date-time | no | time recorded by the SIEM (CRGO *recorded at*) |
| `ocsfClass` | integer or string | no | OCSF 1.9.0 class |
| `parser` | string | no | parser and version (CRGO *parsed by*) |
| `hash` | string | no | hash of the raw event |
| `link` | string | no | link to the event in the SIEM (no credentials) |

### Deduplication

| List | Duplicate when | What happens |
|---|---|---|
| sources | same `id` | a new health observation (if `health` or `healthHistory` is given and not already recorded) is appended and `lastSeen` moves forward; other fields are kept |
| rules | same `id`, or same `ruleId` | same `version`: duplicate, skipped; another `version`: the previous version is kept in `versions[]` and the rule takes the new one (its status change is recorded in `history`) |
| alerts | same `sourceSystem` + `externalId` + `version` (case-insensitive), or same `id` | skipped; the original alert stays as first imported |
| indicators | same `id` or same `stixId` | skipped |
| tests, strategies, gaps, coverage, events | same `id` | skipped |

### Other accepted files

- **Sigma rules** (`.yml`/`.yaml`, several documents separated by `---`): `title` (required), `id` → `ruleId`, `status` (`experimental` → draft, `test`/`stable` → testing, `deprecated`/`unsupported` → retired — never production), `level`, `description`, `author`, `date`, `modified`, `references`, `falsepositives`, `logsource` {`product`, `service`, `category`}, `tags` (`attack.t####[.###]` → techniques), `detection` kept verbatim as text. Re-importing the same Sigma id with a different detection or title creates the next version.
- **STIX 2.1 bundle** (`{"type": "bundle", "objects": [...]}`): `indicator` objects → indicators (pattern, `valid_from`, `valid_until`, `confidence` 0–100, `created_by_ref` → source via `identity` objects, `revoked`); TLP from `object_marking_refs` — TLP 2.0 marking-definition ids, TLP 1.0 ids (WHITE = CLEAR) or `marking-definition` objects in the bundle whose `name` is a TLP label; `sighting` objects → attached to their indicator (`sighting_of_ref`) **and** imported as an alert to triage (`sourceSystem` `STIX sighting`, `externalId` = sighting id). Other object types are counted as skipped.
- **Alerts, JSON list**: an array of *alert* objects, or `{ "alerts": [...] }`.
- **CSV** (comma or tab, header row, case-insensitive; list cells separated by `;`). With *Detect from the file*, the kind is read from the header (a `severity`, `detected` or `rule_id` column → alerts; `cadence_hours`, `health` or `ocsf_class` without `severity` → sources; `value`, `pattern` or `valid_until` → indicators); otherwise choose the kind in the import screen:
  - telemetry sources: `id,name,system,asset,ocsf_class,data_components,parser,parser_version,product,service,category,cadence_hours,last_seen,health,health_date`
  - alerts: `id,external_id,version,source_system,title,rule_id,rule_version,detected,first_seen,severity,confidence,asset,techniques,scenarios,indicators,tlp,triage`
  - indicators: `id,stix_id,type,value,pattern,name,valid_from,valid_until,confidence,confidence_method,source,tlp,labels,techniques`

## SOAR

Format identifier: `crg-soar-import/1`. Read by **SOAR → Overview → Import a SOAR file** (a local file; nothing is fetched from a network). The import is recorded in the data log (`LOG.data('SOAR import', <file name>, <summary>)`) and in `ws.soar.imports` with the SHA-256 of the file.

Local only: the file describes playbooks, cases, approvals and the actions people **recorded**. Nothing in it is executed, and nothing in it authorises an action: the application checks each recorded execution against the recorded approvals and shows the gaps as **audit signals**.

### Document

One UTF-8 JSON object:

| Field | Type | Required | Meaning |
|---|---|---|---|
| `format` | string | yes | exactly `"crg-soar-import/1"`; any other value refuses the whole file |
| `generated` | string (ISO 8601) | no | when the file was produced (informative) |
| `source` | string | no | what produced it (informative) |
| `playbooks` | array of Playbook | no | |
| `gates` | array of Gate | no | |
| `cases` | array of Case | no | |
| `approvals` | array of Approval | no | |
| `executions` | array of Execution | no | |
| `simulations` | array of Simulation | no | |
| `confirmations` | array of Confirmation | no | incident confirmations of imported or existing cases |
| `lessons`, `impacts`, `communications`, `recoveries`, `measurements`, `artefacts` | arrays | no | see "Optional lists" |

Every list is optional. Unknown top-level fields are ignored.

### Import rules

- Records are validated **one by one**. An invalid record is skipped and listed with the reason; the other records are imported.
- A record whose `id` already exists in the same list **replaces** it; otherwise it is added. Identifiers are free strings; the application's own prefixes are `PB-`, `GATE-`, `CASE-`, `APR-`, `EXE-`, `SIM-`, `LL-`, `IMP-`, `COM-`, `REC-`, `MSR-`, `FA-` followed by three digits (e.g. `CASE-007`); using them avoids collisions with records typed later.
- Lists are imported in this order: `playbooks`, `cases`, `gates`, `approvals`, `executions`, `simulations`, `lessons`, `impacts`, `communications`, `recoveries`, `measurements`, `artefacts`, then `confirmations`. References between records are **not** required to resolve (an execution may cite a case that is not there; a warning is listed).
- Dates: `date` = `YYYY-MM-DD`. `datetime` = `YYYY-MM-DDTHH:MM` (seconds optional). A trailing `Z` or offset is accepted but **ignored**: all times are compared as written, so use one time zone throughout a file. Where a field accepts `date|datetime`, a bare date means the start of that day, except `validUntil`, where it means the end of that day (valid through that day).
- Names of people are free strings, compared case-insensitively and trimmed (`"Sam Lead"` = `"sam lead"`).
- Published playbook versions get their SHA-256 **recomputed** from their content; a supplied `sha256` that does not match is replaced and reported as a warning.
- Regulator communications create the regulatory submission in Compliance management (see `communications`).

### Playbook

| Field | Type | Required | Meaning |
|---|---|---|---|
| `id` | string | yes | |
| `name` | string | yes | |
| `purpose` | string | no | |
| `owner` | string | no | person or role |
| `category` | incident category | no | the kind of incident handled |
| `trigger` | object `{kind, conditions}` | no | `kind`: trigger kind (default `manual`); `conditions`: string |
| `scenarios` | array of string | no | risk scenario ids (`S1`…) it addresses — intent only, it never reduces a risk |
| `versions` | array of Version | yes, ≥ 1 | at most one `published` and at most one `draft` |

`current` (the version in force) is set by the import to the `published` version; it is not read from the file.

**Version**

| Field | Type | Required | Meaning |
|---|---|---|---|
| `version` | integer ≥ 1 | yes | unique within the playbook |
| `state` | version state | yes | `published` = in force (frozen); `retired` = superseded (frozen); `draft` = editable |
| `published` | date | yes if `published` | |
| `publishedBy` | string | yes if `published` | person |
| `sha256` | string (64 hex) | no | recomputed for `published` and `retired` versions |
| `steps` | array of Step | no (empty allowed in a draft) | in execution order |

**Step**

| Field | Type | Required | Meaning |
|---|---|---|---|
| `id` | string | yes | unique within the version, e.g. `ST-1`; executions cite it |
| `name` | string | no | |
| `action` | string | yes | the response action, e.g. `isolate host` |
| `riskClass` | risk class | yes | |
| `gate` | string | no | id of the approval gate the step must pass |
| `requiresGate` | boolean | no | the step needs an approval even without a named gate |
| `evidence` | string | no, but a dry run **fails** a step without it | the response evidence expected |
| `criticalAsset` | boolean | no | the step acts on a crown-jewel asset (dry run) |

The hash covers `{playbook, version, trigger{kind, conditions}, steps[{id, name, action, riskClass, gate, requiresGate, evidence}]}` serialised as JSON in that key order (see `canonical()` in `js/soar.js`).

### Gate

| Field | Type | Required | Meaning |
|---|---|---|---|
| `id` | string | yes | |
| `name` | string | yes | |
| `riskClasses` | array of risk class | no | classes that need approval through this gate |
| `criticalAssets` | boolean | no | applies whenever the target is a crown jewel |
| `authorities` | array of string | yes, ≥ 1 | the people or roles who may approve |
| `scope` | string | no | |
| `validFrom`, `validUntil` | date | no | the gate is in force between these dates |

`containment` and `destructive` actions need an approval even when no gate names them (default-deny).

### Case

The SIEM escalation shape `{id, title, source:{kind:'alert', id}, opened, status:'open', severity, alerts:[ids], timeline:[]}` is a valid case.

| Field | Type | Required | Meaning |
|---|---|---|---|
| `id` | string | yes | |
| `title` | string | yes | |
| `opened` | date\|datetime | yes | |
| `status` | case status | no (default `open`) | |
| `severity` | severity | no | |
| `category` | incident category | no | |
| `source` | object `{kind, id}` | no | `kind`: case source kind; `id`: alert id when `kind` = `alert` |
| `alerts` | array of string | no | SIEM alert ids investigated |
| `assignee` | string | no | |
| `assets` | array of string | no | |
| `target` | string | no | main host or account (used by dry runs to test pre-authorisation targets) |
| `activityStart` | datetime | no | start of malicious activity (time to detect, dwell time) |
| `statusDates` | object `{<status>: datetime}` | no | when each status was reached (time to acknowledge, contain, recover) |
| `timeline` | array of `{at: datetime, by: string, text: string}` or of strings | no | |
| `closure` | string | no | closure rationale |
| `notes` | string | no | |
| `incident` | string | no | id of an incident in the incident register already linked; prefer `confirmations` |

A case is **never** an incident by itself. Status in the file is taken as recorded; in the application a case moves one stage at a time.

### Approval

| Field | Type | Required | Meaning |
|---|---|---|---|
| `id` | string | yes | |
| `kind` | approval kind | no (default `specific`) | |
| `gate` | string | no | gate id |
| `requestedBy` | string | yes | person |
| `requested` | date | no | |
| `outcome` | approval outcome | yes | |
| `approver` | string | yes unless `requested` | person; **must differ from `requestedBy`** (no self-approval: the record is skipped) |
| `decidedOn` | date\|datetime | yes unless `requested` | |
| `validFrom` | date\|datetime | yes if `approved` | |
| `validUntil` | date\|datetime | yes for a `pre-authorisation` | expiry |
| `case` | string | no | limits the approval to one case |
| `execution` | string | no | a specific approval of one execution id |
| `action` | string | yes for an `approved` `specific` approval without `execution` | the action approved (compared case-insensitively with the execution's `action`) |
| `riskClasses` | array of risk class | yes, ≥ 1, for a `pre-authorisation` | classes pre-authorised |
| `targets` | array of string | no | targets in scope; empty = any target |
| `scope` | string | no | written scope; a `pre-authorisation` needs `targets`, `case` or `scope` |
| `revokedOn` | date\|datetime | no | |
| `revokedBy` | string | yes if `revokedOn` | |
| `rationale` | string | no | |

### Execution (a manually recorded action)

| Field | Type | Required | Meaning |
|---|---|---|---|
| `id` | string | yes | |
| `case` | string | no | case id |
| `playbook` | string | no | playbook id |
| `version` | integer | no | the playbook version followed (pinned: a later version never changes it) |
| `step` | string | no | step id within that version |
| `action` | string | yes in the application | what was done |
| `riskClass` | risk class | yes in the application | |
| `target` | string | no | host, account or service acted on |
| `criticalAsset` | boolean | no | the target is a crown jewel |
| `performedBy` | string | yes in the application | person |
| `attempt` | string | yes in the application, unique | attempt identifier |
| `started` | datetime | yes | |
| `ended` | datetime | no | |
| `status` | execution status | yes | |
| `approval` | string or array of string | no | approval id(s) relied on |
| `evidence` | array of string | no | response evidence: pointers or `EV-` ids of the shared evidence register |
| `notes` | string | no | |

**Approval check (audit signal).** An execution is gated when its risk class is `containment` or `destructive`, when its step has `requiresGate` or a `gate`, or when a gate in force at `started` covers its risk class (or its crown-jewel target). For a gated execution the application reports, as CRGO `secops/v1` does, one reason when no approval it relied on is valid at `started`:
`absent` (none cited), `not-granted` (outcome not `approved`), `not-corresponding` (other execution, other action, other case, risk class or target outside the pre-authorisation), `wrong-authority` (approver not among the authorities of the gates that apply, or approver = requester), `not-yet-valid` (`decidedOn` or `validFrom` after `started`), `revoked` (`revokedOn` ≤ `started`), `expired` (`validUntil` < `started`). With several approvals cited the most telling reason is shown, in the order expired, revoked, not-yet-valid, wrong-authority, not-corresponding, not-granted.

| Field | Type | Required | Meaning |

### Confirmation

| Field | Type | Required | Meaning |
|---|---|---|---|
| `case` | string | yes | case id (imported or existing) |

## Simulation data

Fictional SIEM and SOAR records for teaching are distributed as **simulation packs** (`crg-simulation-pack/1`): a manifest (case, learning objectives, day-by-day storyline, exercises, expected import counts) with one `crg-siem-import/1` file and one `crg-soar-import/1` file, inline or listed in `files`. The bundled packs are in `data/simulation/` (`index.json`, e.g. `medibec/manifest.json`, `medibec/siem.json`, `medibec/soar.json`).

- **Settings → Simulation data** imports a pack into the current workspace through the importers described above (`importText()` with kind `envelope`, then `importDoc()`), marks every record it added with `simulation: true` and `simPack: <pack id>`, and can remove those records later. It can also generate a pack with AI and validate it before import.
- In a pack, both envelopes carry `"simulation": true` and every record should too (the SIEM importer ignores the field; the marking is applied after the import). Observables use only documentation addresses (RFC 5737, RFC 3849) and reserved domains (`example.com/.net/.org`, `*.example`, `*.test`).
- A pack never contains `confirmations` and never an alert with `triage: "escalated"`: incidents are confirmed by the students.
- How a pack is designed and checked: [SIMULATION-DATA-GUIDE.md](SIMULATION-DATA-GUIDE.md); the schema and the validator: `PACK_SCHEMA` and `validatePack()` in `js/simgen.js`.
